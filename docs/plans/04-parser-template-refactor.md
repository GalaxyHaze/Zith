# Step 4 --- Parser Template Refactor

## Summary

Refactor the generated `Parser<Output>` to eliminate duplicated `TokenStream`
wrappers and introduce a generic `OutputBuilder<Output>` template that hooks
can use to construct the user's output type without manual stack management.

Depends on Steps 1 and 2.

## Design Decisions

- Hooks continue to receive `(Parser<Output> &parser, const Token &token)`.
  Access to `TokenStream` is via `parser.tokenStream()` (which already exists).
- `Parser` no longer wraps `advance()`, `match()`, `matchAll()`,
  `matchLexeme()`, `matchAllLexeme()`, `hasNext()`, `size()`, `empty()`
  around the underlying `TokenStream`. The generator stops emitting these
  wrapper methods. Callers write `parser.tokenStream().advance()`.
- New template `OutputBuilder<Output>` provides a value stack:
  `push(Output)`, `pop() -> Output`, `top() -> Output&`,
  `attach()` (pops top two, attaches child to parent via ADL),
  `close(unsigned count)` (pops N, attaches to new top).
- `parser.rules` gains optional builder declarations:
  `[context Expr builder=true]` activates the builder for that context.
  `[parser] builder: MyBuilder<Output>` lets the user supply a custom
  builder type.

## Implementation Changes

### 4.1 --- Parser de-duplication

- In `generated_parser::Parser<Output>` (generated by `generate.py`):
  - Keep `tokenStream()` (returns `TokenStreamAlias &` and
    `const TokenStreamAlias &`).
  - Remove direct wrapper methods listed above.
  - In `step()`, replace `advance()` with `tokenStream().advance()`.
- `generate.py`: remove the block that emits the wrapper method bodies.
- Migration in tests and `actions.cpp`: change `parser.advance()` to
  `parser.tokenStream().advance()`. This is a mechanical find-and-replace
  within `tests/frontend/parser-test.cpp` and
  `src/frontend/parser/actions.cpp`.

### 4.2 --- OutputBuilder template

New file: `src/common/parser/builder.hpp`

```cpp
namespace common::parser {

template <typename Output>
class OutputBuilder {
public:
    explicit OutputBuilder(memory::Arena &arena);

    void push(Output value);
    Output pop();
    Output &top();
    const Output &top() const noexcept;
    [[nodiscard]] bool empty() const noexcept;
    [[nodiscard]] size_t size() const noexcept;

    // Pops top two; attaches child (old top) to parent (new top)
    // via ADL: attach(parent, child).
    void attach();

    // Pops `count` elements and attaches them as children to the new top.
    // count=0 attaches the current top to the element below it.
    void close(unsigned count = 0);

private:
    memory::DynArray<Output> stack_;
};

} // namespace common::parser
```

- `attach(Output &parent, Output child)` is a free function found via ADL.
  The user defines it in their output type's namespace.
- `close(N)` pops N elements and attaches them as children to the new top.
  Typical pattern: push start marker, process children, close(childCount).

### 4.3 --- parser.rules extensions

New optional field on `[context]`:

```text
[context Expr parent=TopLevel builder=true]
```

`builder=true` causes the generated `Parser` to own a
`common::parser::OutputBuilder<Output>` accessible via `parser.builder()`.

New optional field on `[parser]`:

```text
[parser]
...
builder: MyBuilder<Output>
```

Specifies a custom builder type. Default is
`common::parser::OutputBuilder<Output>` when at least one context
declares `builder=true`.

### 4.4 --- Generator changes

- `generate.py` reads `builder=true` per context and `builder:` type
  from `[parser]`.
- Emits builder member and accessor in `Parser<Output>` class body.
- Emits `#include "common/parser/builder.hpp"` in generated `parser.hpp`
  when builder is enabled.
- Removes the duplicate `TokenStream` wrappers (4.1).
- Validates that `builder=true` only appears on contexts that have at
  least one rule with an action.
- Validates that `push` and `pop` are not used on the same rule when
  builder is active (only one state change per rule).

### 4.5 --- TokenStream access pattern change

The generated `step()` method changes all internal token advances from
bare `advance()` to `tokenStream().advance()`. Example:

```cpp
// Before:
if (token.kind == TokenKind::Fn) {
    hooks::parser::beginModule(*this, token);
    pushState(ParserState::Module);
    advance();
    return true;
}

// After:
if (token.kind == TokenKind::Fn) {
    hooks::parser::beginModule(*this, token);
    pushState(ParserState::Module);
    tokenStream().advance();
    return true;
}
```

Hook signatures remain `(Parser<Output> &parser, const Token &token)`.
If a hook wants to consume extra tokens, it uses
`parser.tokenStream().advance()`.

## Test Plan

- `parser-generated-basics`: update to use `parser.tokenStream().advance()`
  instead of `parser.advance()`. Add test for `OutputBuilder` push/pop/attach
  with a user-provided output type that defines `attach()`.
- `parser-generator-regression`: add a rules variant with `builder=true`
  context, verify the generated code compiles end-to-end.
- Full regression: `ctest --test-dir build --output-on-failure`.
- Verify `step()` produces identical parse behavior for the existing
  `parser.rules` file.

## Assumptions

- Users who need a custom builder type satisfy the same concept
  (push, pop, top, attach, close). Default: `common::parser::OutputBuilder`.
- `attach(Output&, Output)` ADL lookup resolves because `Output` is the
  user's type.
- The builder is optional: contexts without `builder=true` generate no
  builder code, keeping the parser minimal.
- `attach()` in `OutputBuilder` calls the user's ADL `attach(parent, child)`.
  If the user does not define one, a `static_assert` fires at compile time.
