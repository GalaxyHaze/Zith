Structs Finally Work — Rebuilding the Pipeline

2026-07-29

For a long time Zith could declare a struct and then do almost nothing with it. The declaration parsed, the name resolved, and that was the end of the road — no field reads, no literals, no pointers into it. That gap is closed now.

What changed

I added three expression kinds to the modern frontend — Field, Arrow, and StructLiteral — and pushed them through every stage: parser, type table, sema, HIR lowering, and the formatter. So this compiles and runs: 

struct Point {
    x: i32,
    y: i32,
}

fn shift(origin: Point): i32 {
    let moved: Point = Point { x: origin.x + 1, y: origin.y };
    let handle: *Point = &moved;
    handle->x
}

Four things landed together there: a struct literal with named fields, dot access on a value, address-of with unary &, and arrow access through a pointer. Arrow is not a separate mechanism — it desugars to a deref followed by a field read, which kept the HIR surface small.

The boring part that mattered

The interesting work was not the syntax, it was the type table. A struct type now carries a parallel array of field names, and TypeTable::fieldIndex resolves a name to an index. Sema uses it during inference; HIR lowering uses it to emit a positional HirField. Names disappear before code generation, which is exactly what you want — the backend should never do string comparisons to find a field.

Assignment needed care too. p.x = 1 and p->x = 1 mean writing to an lvalue, not producing a value, so lowerAssign learned to treat Field and Arrow targets as addresses rather than reads.

Killing the barrier

Back in July I added a semantic barrier — error E2010, UnsupportedSyntax — that rejected constructs the parser accepted but the compiler could not honour. It was the right call at the time: silently lowering is or ? into Add was worse than an honest error.

With the modern pipeline that barrier is gone from the active path. The old sema still lives under lib/legacy-zith, but nothing in the current build emits E2010. The diagnostic surface is now just E0001, E0000, E2002, and E1006. Fewer codes, each of which actually means something.

What I am not pretending

when still breaks: the parser reads the header and then chokes on the 0 => { } arm syntax. const fn is worse than unimplemented — it parses as a const binding named fn, which is a genuinely confusing failure I need to fix at the keyword level. dyn Trait is unsupported in the type parser, and @ in expression position is still a parse error, which blocks macros and builtins alike.

NRA — the ownership analysis the memory model is built around — is still a pipeline slot with nothing in it. Comptime evaluation likewise. I keep those honest in docs/impl-status.md, verified against zithc check feature by feature rather than against what the spec wishes were true.

What's next

when arm parsing is the next piece, because pattern matching unlocks a lot of ordinary code. After that, const fn needs a real keyword fix, and then I want to start on NRA — it is the largest unimplemented idea in the language and the longer it stays a slot, the more the spec drifts from the compiler.
