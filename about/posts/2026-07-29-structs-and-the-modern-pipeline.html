Structs Finally Work — Rebuilding the Pipeline

2026-07-29

For a long time Zith could declare a struct and then do almost nothing with it. The declaration parsed, the name resolved, and that was the end of the road — no field reads, no literals, no pointers into it. That gap is closed now.

What changed

Three expression kinds went into the modern frontend — Field, Arrow and StructLiteral — and through every stage behind it: parser, type table, sema, HIR lowering, formatter. Which means this compiles and runs: 

struct Point {
    x: i32,
    y: i32,
}

fn shift(origin: Point): i32 {
    let moved: Point = Point { x: origin.x + 1, y: origin.y };
    let handle: *Point = &moved;
    handle->x
}

Four separate things are working in those six lines: a struct literal with named fields, dot access on a value, address-of with unary &, and arrow access through a pointer. Arrow is not its own mechanism — it desugars to a deref followed by a field read, which kept the HIR surface from growing.

The boring part that mattered

The interesting work was not the syntax, it was the type table. A struct type carries a parallel array of field names, and TypeTable::fieldIndex maps a name to an index. Sema uses that during inference; lowering uses it to emit a positional HirField.

So names disappear before code generation, which is exactly the property you want. The backend should never be doing string comparisons to find a field.

Assignment needed its own care. p.x = 1 and p->x = 1 write to an lvalue rather than producing a value, so lowerAssign learned to treat Field and Arrow targets as addresses instead of reads.

Killing the barrier

Back in July I added a semantic barrier — error E2010, UnsupportedSyntax — that rejected constructs the parser accepted but the compiler could not honour. It was the right call at the time: silently lowering is or ? into Add was worse than an honest error.

That barrier is gone from the active path. The old sema still lives under lib/legacy-zith, but nothing in the current build emits E2010, and the diagnostic surface is down to E0001, E0000, E2002 and E1006. Fewer codes, each of which means something.

What I am not pretending

when still breaks: the parser reads the header and then chokes on the 0 => { } arm syntax. const fn is worse than unimplemented — it parses as a const binding named fn, which is a genuinely confusing failure I need to fix at the keyword level. dyn Trait is unsupported in the type parser, and @ in expression position is still a parse error, which blocks macros and builtins alike.

NRA — the ownership analysis the memory model is built around — is still a pipeline slot with nothing in it, and comptime evaluation likewise. I keep those honest in docs/impl-status.md, verified against zithc check feature by feature rather than against what the spec wishes were true.

What's next

when arm parsing, because pattern matching unlocks a lot of ordinary code. Then const fn needs a real keyword fix. Then NRA — it is the largest unimplemented idea in the language, and the longer it stays an empty slot the further the spec drifts from the compiler.
