Macros Actually Expand Now

2026-08-04

For most of Zith's life @ in expression position was a parse error, which meant macros were a chapter in the spec and nothing else. That is over. Normal macros, raw macros, and tag macros all expand through the modern pipeline and lower to HIR.

Resolution by node id

The first version I wrote matched template names against the call site by comparing source spans. It worked on the test I wrote it for and fell apart on everything else — a template used twice produced two expansions whose spans pointed at the same original text, so the second expansion happily resolved to the first one's bindings.

The fix was to stop thinking about text. Each expansion produces fresh nodes with fresh ids, and resolution is keyed by node id, not by where the characters came from. Once that was true, hygiene became a rename pass rather than a scoping trick: a binding introduced by the template gets a new name, every other identifier is looked up in the call-site scope with the module and globals as fallback. 

macro twice(v: expr) {
    v + v
}

fn use_macro(v: i32): i32 {
    @twice(v)
}

The other thing I had to get right is that a template body is not code. It is not name-resolved, not type-checked, and not lowered until it has been expanded at a call site. Analysing it early is tempting — you would catch typos sooner — but it is wrong: the meaning of v does not exist until somebody passes something.

raw macro is the deliberate escape hatch. It splices literally into the call site, names resolve there first, and it can touch the caller's bindings. That is unhygienic by construction and that is the point; it just has to be spelled differently so nobody gets it by accident.

Tag macros

Tag macros are the piece I was least sure about and now like the most. They are an HTML-like statement form with a body and optional named attributes: 

tag macro RunTwice(attributes, body: body) {
    let title = attributes.title;
    body;
    body;
}

fn main(): i32 {
    var total = 0;
    <RunTwice title: 1>
        total = total + 1;
    </RunTwice>
    total
}

They are statement-position only, and misuse has its own diagnostics rather than falling through to a generic parse error: E2017 when a tag macro is used as a value, E2018 for a mismatched closing tag, E2019 for an unknown attribute, E2020 when a macro that takes no attributes is given some.

The C importer met the real world

In parallel the libclang-based header importer stopped being a demo. Variadic functions, array-decayed parameters, va_list, and function-pointer parameters all import now, and — more important than any single feature — a declaration the importer cannot represent is skipped on its own and recorded, instead of failing the header. Real headers contain things I have no plan for; refusing all of stdio.h over one of them was absurd. 

import "stdio.h";

fn main(): i32 {
    printf("v=%d\n", 42);
    0
}

That prints v=42. Getting there took an embarrassing detour: it printed nothing. The compiler was fine and the binary was fine — zithc run was the bug. It captured the child process's output and then tore the capture down before flushing it, so the program's stdout went into a buffer nobody ever read. Now the child's output is forwarded to zithc's own stdout while diagnostics stay on stderr, which is also the behaviour you want if you are piping a program's output anywhere.

What I am not pretending

Macros are not comptime. There is still no compile-time evaluation, no const fn, and no reflection — @appendField and friends remain spec text. Preprocessor macros, globals, bitfields, packed records and flexible arrays do not import, and struct-by-value across the C ABI is unverified, so I do not claim it.
